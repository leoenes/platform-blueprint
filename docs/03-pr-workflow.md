# PR workflow: plan, review, apply, merge

```mermaid
sequenceDiagram
  participant Dev
  participant PR
  participant CI as Terraform CI
  participant AWS
  Dev->>PR: push
  PR->>CI: pull_request
  CI->>CI: changed files → impacted projects → stage 0
  CI->>AWS: plan every project (parallel)
  CI->>PR: one sticky comment: table + plans + fingerprints
  Dev->>PR: review, approve
  Dev->>PR: comment "digger apply"
  PR->>CI: issue_comment
  CI->>CI: snapshot = merge commit; stages by dependency depth
  CI->>AWS: re-plan, compare fingerprint, apply saved plan
  CI->>PR: apply report, reaction 🎉 / 👎
  CI-->>Slack: outcome
  Dev->>PR: merge
```

## Why apply before merge

Main must describe what exists. If the apply happened after merge and
failed, main would be wrong until someone fixed it. Applying from the PR
means a failed apply leaves main untouched and the PR open with the error.
A reminder nags twice a day about PRs that were applied but not merged.

## The inventory is generated

`digger.yml` lists one project per Terragrunt instance with
`include_patterns` (what changes affect it) and `depends_on` (what must
apply first). It is generated by `generate-inventory.sh` from the directory
tree and checked for staleness on every PR:

- an instance is any `environments/<stage>/<leader>/<region>/terragrunt.hcl`
- a layer declares what it needs in `layer.yaml` (`depends_on: [network, iam-github]`)
- the generator resolves each dependency to the closest instance: same
  tenant and region, else same tenant, else a shared instance in the same
  region, else any shared instance. It never makes prod depend on nonprod.
- `layer@stage/leader[/region]` pins an instance; `project.yaml` in an
  instance directory adds instance-specific dependencies (the Transit Gateway
  peering accepter).

A new region is new instance directories and nothing else.

## Impacted projects

`compute-impacted.sh` turns the inventory and the diff into stages:

1. Lists changed files between base and head.
2. A project is impacted if a file is under its `dir` or matches an
   `include_pattern` (globs converted to anchored regexes).
3. `depends_on` only orders; it never adds projects. A change to the network
   layer does not re-apply every cluster.
4. Depth = `1 + max(depth(parents))` over impacted parents only. Plans are
   flattened to stage 0; applies and drift use the real depth.
5. One matrix per stage goes to a reusable workflow. Stage N runs after N-1,
   and in apply mode only if N-1 succeeded.

## The plan fingerprint

The thing reviewed must be the thing applied. On plan, each project's plan is
reduced to its semantic content (resource changes that are not no-ops,
sorted), hashed with a secret key, and written into the PR comment as a
hidden marker:

```
<!-- tf-plan-fingerprint-v1 project=eks-nonprod-uk head=<sha> sha256=<hash> -->
```

On apply, the project is re-planned from the same snapshot and the hash must
match. If the world moved (someone clicked in the console, a parent changed
an output), the apply refuses with "approved plan changed, re-plan". If it
matches, the *saved plan file* is applied, not a fresh plan.

## Guards on apply

- The commenter has write permission on the repo.
- The PR is mergeable and has an approval on the current head.
- The snapshot is the merge commit at comment time; a push during the run
  does not change what is applied, and re-running a failed apply job is
  blocked (post a new comment instead).
- Per-state concurrency group `tf-state-<dir>`: plans, applies and drift on
  the same state queue; nothing is cancelled.
- `max-parallel: 6` so one PR cannot occupy every runner.
- Applies are never retried automatically. A partial apply is a human
  decision.

## What the PR sees

One comment per mode, updated in place:

| Stage | Project | Result | Summary |
| --- | --- | --- | --- |
| 0 | `network-eu-west-2` | ✅ OK | Plan: 2 to add, 0 to change, 0 to destroy. |
| 1 | `eks-nonprod-uk` | ✅ OK | No changes |

Projects with changes or failures expand to the filtered plan output.
Unchanged projects stay on one line. Missing results are counted and block
the apply.
